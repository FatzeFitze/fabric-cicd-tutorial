# Service connections, managed identities and federation

In Unit 8, you queue the pipeline with your Azure DevOps account. An authorized pipeline task then signs in as a user-assigned managed identity (UAMI) to read Fabric. A UAMI is a reusable Azure resource with its own Microsoft Entra service principal and a lifecycle independent of the agent. The Azure DevOps service connection stores the sign-in configuration and controls which pipelines can use it. [Managed identities overview](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview) · [Azure DevOps service connections](https://learn.microsoft.com/en-us/azure/devops/pipelines/library/service-endpoints?view=azure-devops).

## How the sign-in works

1. Azure DevOps authorizes the pipeline to use the named service connection and supplies a short-lived identity assertion to the task.
2. Microsoft Entra compares the assertion's **issuer** (who issued it), **subject** (which connection it represents) and **audience** (who may accept it) with the federated credential on the UAMI. The **Managed identity** setup creates that credential when you save. With manual setup, copy the issuer and subject from Azure DevOps into the credential on the UAMI. The token-exchange audience in Azure public cloud is `api://AzureADTokenExchange`.
3. The Azure CLI uses the assertion to authenticate as the UAMI, then requests an access token for `https://api.fabric.microsoft.com`. Fabric checks its own tenant and workspace permissions for that identity. The connection needs no stored client secret. [Set up federation manually](https://learn.microsoft.com/en-us/azure/devops/pipelines/release/configure-workload-identity?tabs=managed-identity&view=azure-devops) · [Trust on a UAMI](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation-create-trust-user-assigned-managed-identity) · [Fabric API identity support](https://learn.microsoft.com/en-us/rest/api/fabric/articles/identity-support).

In the workshop form you select the UAMI by name. A manual connection takes its **client ID**. An administrator uses the UAMI's **principal ID** (the object ID of its service principal) when assigning access by ID. The **tenant ID** identifies the Microsoft Entra directory. The UAMI display name in the workshop YAML is a label for the release record. [Automate workload identity service connections](https://learn.microsoft.com/en-us/azure/devops/pipelines/release/automate-service-connections?view=azure-devops).

## Who needs which permissions?

| Action | Who needs access and where |
| --- | --- |
| Create the connection | The learner needs the service connection Creator role or equivalent administrative access in the Azure DevOps project. The connection creator can authorize individual pipelines. [Azure Pipelines security](https://learn.microsoft.com/en-us/azure/devops/pipelines/policies/permissions?view=azure-devops#service-connections) |
| Register federation | Whoever adds the credential needs `Microsoft.ManagedIdentity/userAssignedIdentities/federatedIdentityCredentials/write` on the assigned UAMI. Portal use also needs read access to find the identity. This permission can establish new ways to sign in as the UAMI, so delegate it only on a dedicated identity or have its owner register the credential. [Azure identity permissions](https://learn.microsoft.com/en-us/azure/role-based-access-control/permissions/identity) |
| Assign an Azure role | The person assigning the role needs `Microsoft.Authorization/roleAssignments/write` at the target scope, for example through Role Based Access Control Administrator. The facilitator can assign the UAMI's role ahead of time. The learner then needs no role-assignment permission for the manual connection. [Azure role assignment prerequisites](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-steps) |
| Access Fabric | The UAMI needs access under the Fabric API tenant settings. A team member with workspace Admin grants the UAMI Contributor for later item publishing. The Unit 8 reads alone require Viewer. Runtime and connection access depend on the workload. [Fabric workspace roles](https://learn.microsoft.com/en-us/fabric/fundamentals/roles-workspaces) · [List Items](https://learn.microsoft.com/en-us/rest/api/fabric/core/items/list-items) |

## Why does the connection ask for an Azure scope?

The **Azure Resource Manager** form uses the first subscription and resource group to locate the UAMI. Its **Azure scope** section selects the subscription and optional resource group for the service connection's Azure access. In the workshop, use the supplied resource group in that section. The release mask selects Fabric workspaces by ID and workspace roles control access to them. [Managed identity connection fields](https://learn.microsoft.com/en-us/azure/devops/pipelines/library/connect-to-azure?view=azure-devops#create-a-service-connection-for-an-existing-user-assigned-managed-identity).

The preflight calls Fabric, but the `AzureCLI@2` task prepares an Azure CLI session before it runs the script. The task allows a federated sign-in without subscriptions and then tries to select the subscription if the connection specifies one. A UAMI can therefore pass federation and still fail at subscription selection. Azure RBAC is relevant to this setup step. Fabric permissions determine what the script can read or change. [Azure CLI task implementation](https://github.com/microsoft/azure-pipelines-tasks/blob/master/Tasks/AzureCLIV2/azureclitask.ts) · [Azure CLI subscription selection](https://learn.microsoft.com/en-us/cli/azure/manage-azure-subscriptions-azure-cli?view=azure-cli-latest).

In a production setup, the identity owner can control who adds federated credentials, and the release owner can control which pipelines may use the production connection. Separate Dev, Test and Prod UAMIs and connections let those permissions be managed independently. [Service connection permissions and checks](https://learn.microsoft.com/en-us/azure/devops/pipelines/library/service-endpoints?view=azure-devops).
